# API 연동 Gap Analysis (2026-11-23, `integration/screens-api` 783aa58 + 미커밋 변경)

조사와 계획만 담은 문서다. 코드는 수정하지 않았다.

## 0. 조사 방법과 증거 수준

| 근거 | 내용 | 신뢰 수준 |
|---|---|---|
| 운영 서버 `GET /openapi.json` (읽기 전용 1회) | 21개 경로, 43개 스키마. 프론트 `types.ts`의 속성명이 전부 존재함(자동 대조) | 배포된 계약. 값 의미는 보장하지 않음 |
| `pacebeat-team/pacebeat-backend` 저장소(`gh api`, 읽기 전용) | `app/routers`, `app/schemas`, `app/services`, `backend-specification.md`. 마지막 커밋 2026-11-19 | 코드를 읽은 결과. **배포본과 같다는 보장은 없고 실행해 보지 않았다** |
| 프론트 코드 | `src/lib/api`, `src/lib/auth`, `src/features/serverSync`, 화면, 라우터 | 정적 분석 |
| 자동 테스트 | Node 1456, Vitest 16 (가짜 fetch·저장소) | **실서버 검증이 아니다** |

실서버에는 `GET /health`, `GET /openapi.json`만 요청했다(이전 조사 포함). 데이터를 바꾸는 요청과 토큰이 필요한 요청은 하지 않았다. 아래에서 "실서버 검증 완료"라고 부를 수 있는 것은 `GET /health`의 `{"status":"ok","database":"connected"}` 응답뿐이다.

## 1. 가장 큰 사실 두 가지

1. **앱에 로그인 수단이 없다.** `authService`에는 `setSession`, `refresh`, `signOut`만 있고 GoTrue 로그인 호출(OTP·소셜·비밀번호·익명)이 없다. `setSession`을 부르는 앱 코드도 없다(테스트에서만 호출). `AccountPage`는 "계정 연결: 연결 안 됨"과 "이 시안에서는 실제 로그인을 하지 않아요"를 표시한다. 따라서 **지금 배포해도 어떤 사용자도 `signedIn`이 되지 않고, 이미 구현한 동기화 코드는 전부 휴면 상태**다.
2. **화면은 서버 API를 직접 쓰지 않는다.** `lib/api`·`serverSync`를 import하는 곳은 `main.tsx`뿐이다. 연결은 store 구독(`syncWiring.ts`)으로만 이뤄지고, Home·Growth·Posture·Insole·Export·Delete 화면은 로컬 데이터만 읽는다. TanStack Query 옵션(`queries.ts`)은 어느 화면도 쓰지 않는다.

## 7. 백엔드 담당자에게 보낼 질문 (중복 제거)

각 질문에 필요한 자료를 함께 적었다. 응답 예시는 개발·테스트 환경에서만 받는다.

| # | 질문 | 필요한 명세·응답 예시 |
|---|---|---|
| Q1 | **로그인 방식**(이메일 OTP / 소셜 / 비밀번호 / 익명 로그인)과 앱에서 쓸 방식. anon(publishable) 키. Redirect URL·Site URL 목록. 익명 로그인을 허용하면 게스트가 서버에 저장될 수 있는지 | Supabase Auth 설정(활성 provider), 선택한 방식의 토큰 응답 예시(값은 가림), 키 전달 |
| Q2 | **JWT 서명 방식.** 백엔드는 HS256+`SUPABASE_JWT_SECRET`만 검증한다. Supabase 프로젝트가 레거시 HS256 secret을 쓰는지 비대칭 서명 키를 쓰는지, 운영 서버에 secret이 설정돼 있는지 | 실제 access token의 헤더(`alg`, `kid`)와 `sub`만 담은 예시(서명·secret 제외), 서버 환경변수 설정 확인 |
| Q3 | **개발·스테이징 서버와 테스트 계정.** 실서버 쓰기 검증을 어디서 해도 되는지, 운영 DB에 테스트 데이터를 써도 되는지, 정리 방법 | 환경 주소, 테스트 계정 2개(계정 격리 검증용), 초기화 절차 |
| Q4 | **`POST /runs` upsert 정책.** 재시도 시 `mode/completion/started_at/target_*/music_track_id`를 갱신하지 않는 것이 의도인지, `posture_report`를 빼고 다시 보내면 기존 리포트를 남기는 것이 의도인지, 갱신인데도 201인지, `pace_status`·`cadence_status`의 판정 기준과 미전송 시 기본값(`valid`) 의미 | 같은 `client_session_id`로 두 번 보낸 요청·응답 쌍, 상태값 판정표 |
| Q5 | **`PATCH /users/me`의 null 의미.** 코드상 null을 보내면 값이 지워진다(생략하면 유지). 이것이 의도인지, 프론트가 생략 방식으로 보내도 되는지 | 부분 필드만 보낸 요청·응답 예시, null 전송 예시 |
| Q6 | **`PATCH /users/me/guidance`는 전체 교체인가.** 부분 갱신(필드 생략)을 지원할 수 있는지, 아니면 프론트가 GET으로 읽어 합쳐 4필드를 모두 보내야 하는지. 박자 안내·자동 일시정지·안내 빈도(선택지)를 서버에 둘 계획이 있는지 | 요청·응답 예시, 필드 추가 계획 |
| Q7 | **기초 측정 `quality_status`.** `valid`를 보내야 기준 페이스가 저장되는 것이 맞는지(프론트는 유효 2분 이상일 때 `valid`를 보낼 예정), `GET baseline`이 기록 없음과 건너뜀을 어떻게 구분하는지, `onboarding_completed_at` 사용 의도 | PUT·GET 요청·응답 예시(valid, insufficient_data, skipped, 미측정) |
| Q8 | **Growth·Home 집계 기준.** 롤링 UTC 단일 버킷을 의도한 것인지, KST 달력 주(월요일 시작)·이전 기간 비교·일/주 시계열 응답을 제공할 계획이 있는지, 평균 페이스를 거리 가중으로 할지, 서버에 없는 로컬 전용 기록을 어떻게 볼지 | 원하는 응답 스키마와 예시, 시간대·주 시작 요일 결정, 기간 경계 예시 |
| Q9 | **개별 러닝 기록 삭제 API**가 필요한지(없다면 프론트의 개별 삭제는 로컬 전용이며 서버에서 다시 가져올 수 있음). 삭제 후 재가져오기 방지(tombstone) 방식 | 엔드포인트 명세 또는 "만들지 않음" 결정 |
| Q10 | **`DELETE /users/me`의 범위.** 앱 데이터만 지우고 Supabase 계정은 남기는 것이 의도인지, 계정(auth.users)도 지워야 하는지(서비스 롤 필요), 삭제 후 `GET /users/me`가 빈 프로필을 다시 만드는 동작이 의도인지, 응답 시간·실패 시 부분 삭제 여부(트랜잭션) | 삭제 정책서, 삭제 전후 응답 예시 |
| Q11 | **데이터 내보내기 계약.** 현재 JSON 본문 직접 응답(테이블 행 그대로)의 필드와 안정성을 계약으로 볼 수 있는지, 크기·속도 한계, 호출 횟수 제한, 민감 필드 포함 범위, 파일 다운로드 방식이 필요한지 | 응답 스키마와 실제 응답 예시(개인정보 마스킹) |
| Q12 | **`GET /runs` 확장.** 기록이 늘어도 전체 배열을 반환할 것인지, limit·cursor·`updated_since`를 추가할 계획이 있는지, `from`/`to`가 포함 범위인지 | 정책 결정, 필요하면 스키마 |
| Q13 | **음악 프리셋.** `music_presets.track_id`가 프론트 정적 트랙 id와 같은지(예: 앱의 `music_track_id`가 프리셋에 없으면 어떻게 되는지), 서버를 기준 목록으로 쓸지 | `GET /music/presets` 응답 예시 |
| Q14 | **자세 리포트 SDK 계약**(SDK 담당 포함). 구역 수·의미·순서, 좌우 방향, 하중 비율 합과 단위, 접지 시간 산출, `landing_pattern`·`feedback_items`의 값 목록, 한쪽 연결의 정의, 앱이 요약해서 보내는지 SDK가 요약을 주는지 | SDK 출력 예시(양쪽·한쪽·미연결), `PostureReportPayload`와 필드별 대응표 |
| Q15 | **인솔 연결 상태 보고 주체.** `is_connected`·`battery_pct`·`signal_quality`를 누가 언제 PATCH하는지, 등록(POST) 시점 | 상태 전이도, 요청 예시 |
| Q16 | **운영 설정.** Netlify 주소를 `CORS_ORIGINS`에, 같은 주소를 Supabase Redirect URLs에 추가. 인증 실패 메시지에 예외 내용이 그대로 노출되는 점 | 최종 도메인 목록 |

## 8. 선행 작업 순서와 완료 판정 기준

표기: **자동**은 가짜 fetch·저장소 테스트, **스테이징**은 Q3의 테스트 환경에서의 실서버 검증이다. 자동 테스트 통과를 "실서버 검증 완료"로 보고하지 않는다.

### 단계 0. 결정과 환경 (코드 없음, 모든 단계의 선행)
- 필요: Q1, Q2, Q3, Q16 답변, anon key 수령, 테스트 계정 2개.
- 완료 기준: 로그인 방식 확정, 토큰 `alg` 확인, 스테이징 주소와 테스트 계정이 있음, 서버 쓰기를 해도 되는 곳이 명시됨.

### 단계 1. 계약 정합 수정 (프론트만, 단계 0과 병행 가능)
- 작업: G1(기초 측정 `quality_status`), G2(프로필 PATCH 생략 방식과 pull 이후 전송 순서), G3(안내 설정은 Q6 답변 전까지 현재 동작 유지, 위험은 문서화), G5·G6(요청 전 검증, 0ms·0거리 구간 처리와 "서버에 올라가지 않은 기록" 상태), G11(낡은 문서·주석 정정). **OpenAPI 계약 테스트 추가**: 저장한 `openapi.json`(스냅샷)에 대해 프론트가 만드는 모든 요청 본문을 스키마와 대조하고, 서버 검증기의 강제 규칙(G1, G6 경계)을 케이스로 포함.
- 선행: 없음(G3·G5는 Q4·Q6 답변이 있으면 확정).
- 완료 기준: 계약 테스트가 G1·G2 수정 전 코드에서 실패하고 수정 후 통과(변이 검증). 기존 테스트 전부 통과. 화면·정책(GPS·자동 일시정지·세션 복원·게스트 흐름)은 변경 없음. 서버 값 판정은 아직 "미검증".

### 단계 2. 로그인 (선행: 단계 0)
- 작업: 선택된 방식의 GoTrue 호출, 로그인·로그아웃 UI(`AccountPage` 계정 연결 행), `setSession` 연결, redirect 처리, anon key 환경변수, 오류·취소 처리, 게스트→로그인 안내(자동 이전 금지, A6 정책).
- 완료 기준: 자동 테스트(성공·실패·취소·만료·다른 탭), 스테이징에서 실제 계정 로그인 후 `GET /users/me` 200, 로그아웃 후 게스트 상태, 토큰·키가 콘솔·저장소 외에 노출되지 않음.

### 단계 3. 핵심 동기화 실서버 검증 (선행: 단계 1, 단계 2, 단계 0의 스테이징 환경)
- 항목: 프로필·동의 저장과 다른 기기 복원, 기초 측정 PUT·GET(G1 수정 확인), 러닝 저장·재시도 멱등(같은 `client_session_id` 두 번 → 서버에 1건), 목록·상세 가져오기, 회고 PATCH, 오프라인 저장 후 복구, 401 갱신, 계정 A→B 전환 시 데이터 혼입 없음(테스트 계정 2개), 서버 오류 시 로컬 보존.
- 완료 기준: 각 항목의 실제 요청·응답을 기록(토큰 제외)하고 기대와 일치. 실패 항목은 수정 후 재검증. 이 단계가 끝나기 전에는 어떤 문서·보고에도 "연동 완료"를 쓰지 않는다.

### 단계 4. 삭제·내보내기 (선행: Q9·Q10·Q11, 단계 3)
- 작업: 계정·데이터 삭제 연결(확인 단계, 서버 실패 시 로컬 보존 여부, 완료 후 상태), 내보내기 연결 또는 로컬 내보내기 유지 결정.
- 완료 기준: 정책서와 일치하는 동작, 삭제 후 재가져오기가 일어나지 않음(스테이징 확인), 자동 테스트와 스테이징 검증 모두 통과.

### 단계 5. Home·Growth 결정과 연결 (선행: Q8, 단계 3)
- 작업: 결정에 따라 (a) 로컬 집계 유지 + 서버 값을 보조 표시하지 않음, (b) 서버가 달력 기준 응답을 제공하면 연결. 서버·로컬 불일치 허용 범위 명시.
- 완료 기준: 같은 기록에서 서버 값과 화면 값이 정해진 기준으로 일치, 기록 없음은 0이 아니라 빈 상태.

### 단계 6. 안내·인솔·자세 (선행: Q6·Q14·Q15, SDK)
- 작업: 안내 설정 필드 확장, 인솔 상태 보고, 자세 리포트 전송과 표시.
- 완료 기준: SDK 계약서 기준 대응표, 실제 기기 데이터로 양쪽·한쪽·미연결 검증. 기기 없이는 완료로 표시하지 않음.

### 단계 7. 배포 환경 통합 검증 (선행: 단계 3, Netlify 주소)
- 작업: Netlify 배포 후 CORS·Redirect URL 적용, 배포 도메인에서 로그인·저장·불러오기, 직접 경로 새로고침, iPhone Safari 실기기 확인.
- 완료 기준: `docs/deploy-netlify.md` 4절 경로 전부 정상, 배포 도메인에서 단계 3 항목 재확인, 실기기 확인 기록(`docs/run-real-device-checklist.md`).

## 9. 유지하는 정책 (변경 없음)
계정별 격리, guest·legacy 보존과 자동 귀속 금지, 로컬 우선 저장, 로컬 기록은 서버 값으로 덮지 않음, 재시도 정책(네트워크·5xx·429는 backoff, 401은 로그인 후 재개, 그 밖의 4xx는 `rejected`), 0·추정값 금지(null 유지), GPS·자동 일시정지·세션 복원·자세 리포트·게스트 흐름 정책.

## 11. 단계 1 진행 결과 (프론트만, 2026-11-23, 커밋하지 않음)

| 항목 | 상태 | 내용 |
|---|---|---|
| G2 프로필 PATCH null 덮어쓰기 | 수정 | 미입력은 필드 생략. 출생연도·성별·키·몸무게는 사용자가 있던 값을 직접 지웠을 때만 null(`CLEARABLE_PROFILE_FIELDS`). 닉네임·경험·주간 횟수는 지우는 화면이 없어 항상 생략. 지우기는 대기 작업(`profileClears`)에 저장되어 보내지 못한 채 다른 수정이 쌓여도 유지된다. 이전 버전이 저장한 스냅샷의 null은 보내기 직전에 걸러진다(`sanitizeProfileRequest`) |
| G1 기초 측정 `quality_status` | 수정(근거와 한계 있음) | 기준 페이스가 있는 측정(앱의 `computeBaselinePace`가 채택)은 `valid`를 보낸다. 기준 페이스가 없으면 값을 보내지 않는다(미확정, `gps_poor`·`insufficient_data`를 추측하지 않음). 앱에는 GPS 품질을 따로 판정하는 기준이 없고, `valid`의 정확한 의미는 Q7 답변이 필요하다 |

| G5 `pace_status`·`cadence_status` | 미해결 | 판정 기준 미확정이라 보내지 않음(서버 기본값 `valid`/`no_data`). Q4 |
