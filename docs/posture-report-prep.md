# ⑦ 자세 리포트 사전 준비와 설계 정책

상태: **사전 준비 단계. 구현은 시작하지 않았다.** 코드, 타입, 테스트, fixture는 바뀐 것이 없다.
기존 `POSTURE / No data` 화면과 "데이터가 없으면 값을 표시하지 않는다"는 정책은 그대로다. 예시값·추정값은 앱에 노출하지 않는다.
관련: 계획서 ⑦(`POSTURE / Report`, `POSTURE / One side`), #65, PR #68, ADR-003(페이스 sec/km)·ADR-004(미측정은 null, 0 금지).

## 1. 확정한 데이터 정책

### A. 손상된 `sensorReport`
- `sensorReport`가 누락되거나 잘못된 값을 담고 있어도 러닝 기록 전체를 무효로 하지 않는다.
- 유효하지 않은 `sensorReport`만 폐기(null 취급)하고, 거리·시간·페이스 등 러닝 기록은 보존한다.
- `sensorReport`가 null인 기존 기록은 계속 유효하다.
- 리포트 검증은 러닝 기록 검증과 분리한다(리포트 검증 실패가 기록 검증 결과를 바꾸지 않는다).
- 잘못된 값을 0으로 바꾸지 않는다. 값을 알 수 없으면 null이거나 생략이다.
- 현재 코드와의 차이(구현 시 바꿀 부분): `runStorage.ts`의 `isRunRecord`는 `sensorReport !== null`이면 기록 전체를 거부한다. 이 동작은 위 정책과 맞지 않으므로 구현 단계에서 "리포트만 폐기"로 바꾼다. 지금은 `sensorReport`가 항상 null이라 문제가 되지 않는다.

### B. 센서 데이터 저장
- 러닝 기록에는 **최종 자세 리포트 요약**만 저장한다.
- 원시 센서 샘플과 측정 스트림은 영구 저장하지 않는다.
- SDK 계약이 확정되기 전까지 필드, 단위, 배열 구조를 임의로 만들지 않는다.
- SDK가 원시 샘플만 제공하면, 앱이 요약하는 데 필요한 최소 처리 방식을 별도로 검토한다(이 문서의 범위 밖).

### C. 데이터 내보내기
- 기본 CSV/JSON 내보내기에는 `sensorReport`를 포함하지 않는다.
- 기존 필드와 파일 구조(`recordId, date, mode, distanceKm, durationSec, paceSecPerKm`)를 유지하고 기존 내보내기 테스트를 유지한다.
- 센서 데이터 포함이 필요해지면 별도 정책 결정과 사용자 확인을 거친다.

### D. 세션 복원(#48)
- #48의 기존 복원 정책과 범위를 바꾸지 않는다.
- 원시 센서 스트림을 세션 스냅샷에 추가하지 않는다.
- 새로고침 후 복원된 세션은 기존처럼 일시정지 상태로 복원한다.
- 센서 재연결과 새 측정 데이터 수집은 실제 SDK 연동 단계에서 따로 설계한다.

### 정책이 삭제 기능(⑥)에 주는 영향
`sensorReport`는 러닝 기록 안에 들어가므로 기록 키 삭제만으로 함께 지워진다. 별도 키에 센서 데이터를 두지 않는다는 정책이므로 삭제 대상 확장은 필요 없다.

## 2. SDK 담당자 확인 질문 (전달용, 아직 전달하지 않음)

### 필수 확인
1. **압력 구역**: 한쪽 발당 구역 수, 각 구역의 의미(예: 앞발·중간·뒤꿈치), 배열 인덱스 순서. 좌우 인덱스가 같은 방향인지 거울 반전인지.
2. **압력 단위와 유효 범위**: N, kPa, ADC 원시값, 정규화 값 중 무엇인지와 최소·최대. "착지 압력 분포"가 구역별 원시 압력인지, 구역 간 비율인지, 러닝 전체 평균인지, 걸음별 값인지.
3. **좌우 측정 데이터 제공 구조**: 좌우가 하나의 레코드로 오는지 독립 두 스트림인지. 좌우 장치 식별 방법과 좌우가 바뀌어 연결될 가능성. 러닝 요약을 SDK가 집계해 주는지, 앱이 집계해야 하는지.
4. **한쪽만 측정된 경우의 표현**: 해당 쪽 필드가 null인지, 필드 생략인지, 별도 플래그인지. 러닝 중 한쪽이 끊겼다 복구된 경우의 구간 정보. "한쪽만 측정"의 기준이 러닝 전체인지 일부 구간인지. 양쪽 끊김과 처음부터 연결 없음의 구분.
5. **좌우 균형값**: SDK가 제공하는지, 단위(%, 비율), "균형 양호"를 판정하는 기준과 그 기준을 정하는 주체(SDK/기획).
6. **착지 유형(뒤꿈치·중간·앞꿈치 등)**: 계산 주체(SDK/앱)와 판정 기준.
7. **측정 누락·실패·오류 표현**: 구역별 개별 실패, 센서 이상, 범위 밖 값, NaN의 표현(null, -1, 코드값). 0과 "측정 없음"의 구분. 오류 사유 코드(통신 끊김, 센서 불량, 착용 불량) 제공 여부.

### 추가 확인
8. **샘플링 주기와 데이터량**: 러닝 한 번당 데이터 크기(요약만 저장하므로 저장 용량보다는 수집·집계 부담 확인용).
9. **측정 시각과 일시정지 처리**: 샘플 시각의 기준(부팅 후 시간, epoch)과 시계 오차 보정. 앱의 `startedAt`·`endedAt`과의 대응. 일시정지·재개 구간의 센서 데이터 처리.
10. **신뢰도 필드**: `signalQuality: good|fair|poor|unavailable`(기존 mock) 같은 값이 실제로 오는지와 값별 의미.
11. **최소 유효 측정 기준**: 리포트로 보여줄 최소 걸음 수·시간·유효 샘플 비율, 미달 시 No data로 처리하는지.
12. **계약 버전과 호환 정책**: 버전 필드 유무, 변경 시 호환 정책.
13. **동반 항목 확인**: 케이던스·가속도·자이로가 `sensorReport`에 함께 들어오는지, Figma Report 화면이 쓰는 항목은 무엇인지.

(앞서 보고한 21개 질문을 위 13개 묶음으로 합쳤다. 항목이 빠진 것은 없다.)

## 3. Figma 확인 준비

대상 프레임: `POSTURE / Report`(12991:8436), `POSTURE / One side`(12991:8536), `POSTURE / No data`(12991:8510).
**프레임을 확인하기 전에는 디자인 세부 사항을 추측하거나 확정하지 않는다.** 인증 복구 후 확인할 항목:

1. 구조: 프레임 크기, 섹션 순서, 헤더·CTA 영역, 스크롤과 safe-area
2. 요소별 데이터 매핑표: 각 숫자·그래프·라벨이 계약의 어느 필드에서 오는지. 매핑이 없는 요소는 데이터 없음 시 생략 대상인지 표시
3. 좌우 균형 카드: 표기 방식(퍼센트, 막대, 좌우 라벨), 균형 판정이 색이나 문구로 나뉘는지와 임계값
4. 착지 압력 분포: 그림 형태(발 그림, 막대), 구역 수가 계약과 일치하는지, 색상 스케일과 범례
5. One side: 한쪽만 측정 시 빠지는 요소, 안내 문구, 어느 쪽 데이터인지의 표시
6. 상태: Report의 Loading·Error·부분 데이터 프레임 유무(없으면 "Figma 미정"으로 기록)
7. 문구: 모든 텍스트를 목록화해 미확정 문구는 `docs/unconfirmed-copy.md`에 추가(임의 문구 금지)
8. 디자인 시스템 재사용: 색 토큰, 공통 컴포넌트(StateCard 등), 새로 필요한 컴포넌트, 에셋(`insole-left.svg`, `insole-right.svg` 등 기존 것)
9. 상호작용: 뒤로가기, CTA("인솔 연결 확인" 유지 여부), 탭 가능한 요소
10. 반응형: 360/390/430px에서 줄바꿈, 고정 너비, 그래프 비율 규칙
